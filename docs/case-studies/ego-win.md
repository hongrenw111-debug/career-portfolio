# Case Study 05 — ego-win：ego lite 官方 harness 的 Windows 宿主

## 结论

当前完成的是**本地可用的 Windows 移植层**：用 CDP 实现 ego lite 依赖的 `globalThis.ego` 原生绑定，上游 SDK 逐字节复用不做改动，63 个单元测试全绿、上游真实浏览器套件 68/69 通过。仓库尚未公开。

## Constraint

- ego lite 是 macOS 应用。它的 agent SDK 开源（MIT），但运行在一个闭源浏览器注入的 `globalThis.ego` 原生绑定上，Windows 上整条工具链不可用。
- 重写一遍上层 API 是最直觉的做法，也是代价最高的：两套实现会持续漂移，而语义细节（快照嵌套、iframe 内 ref、跨导航后 ref 失效）靠猜必然出错。
- 上游约 83 万字节代码，任何逐行移植都会引入无法枚举的回归面。

## Decision

- **把移植面收紧到接缝那一层**：只实现原版由浏览器注入的 15 个原生绑定，其余全部复用上游。判断依据是「哪一层是平台相关的」——Page 模型、refs、定位符、等待、弹窗、下载、站点 learnings 都是平台无关的，它们本就该原样运行。
- **逐字节 vendored**：上游 SDK 以 `citrolabs/ego-lite@4cf7935` 固定 commit 存放于 `vendor/sdk/index.js`，禁止手改；本移植只拥有绑定层以下的部分。
- **正确性由上游裁定**：不靠自写断言证明语义对，而是跑上游的真实浏览器套件。绿了就说明绑定层符合 SDK 对原生侧的预期。
- **补一层功能测试看不见的闸门**：自建组合套件，专测两个功能相遇处——那里最容易被单元测试漏掉。

## Mechanism

```text
上游 SDK（逐字节 vendored，不改）
→ globalThis.ego 原生绑定（本移植实现）
  ├─ 任务空间 → Chrome 浏览器上下文
  ├─ 标签页归属认领
  ├─ 无障碍快照渲染（真实嵌套 / 跨进程 iframe / 逐 frame ref 身份）
  └─ 页内光标与浏览器生命周期
→ CDP 会话
→ 系统已有的 Edge / Chrome / Brave
```

## Evidence

- 2026-10-22 实测 `npm test`：**63/63 通过**。
- 上游真实浏览器套件：**68/69** 个 case 通过。唯一失败项 `Page keyboard interface` 卡在剪贴板粘贴。
- 组合套件 `npm run combo`：10 个场景各自独立任务空间运行；它发现了上游套件看不见的 `snapshotFast` ref 注册缺陷，因此被设为绑定层改动后的固定闸门。
- 登录态持久性实测：任务空间共享浏览器 profile，持久 Cookie 跨浏览器重启与跨新任务空间仍可见。

## 当前边界

- **剪贴板**：headless 下该浏览器配置读不到系统剪贴板，`page.keyboard.paste` 插不进内容，纯文本需改用 `insertText()`。是否有头模式下同样失败尚未实测，不作结论。
- **仓库未公开**：没有 remote，公开前需完成脱敏与审查。项目看板里有 20 余条 Windows 专属踩坑记录待整理。
- **仅覆盖 Windows + Chromium 系**，Firefox 与跨平台未做。

## 为什么这个案例值得讲

它不是「我写了个更好的浏览器自动化」，而是**我判断出了真正的接缝在哪**。上游缺的不是功能，是一层被闭源浏览器挡住的原生绑定；补这一层，整套能力就活了。这个判断比多写一万行代码更难，也更容易被追问细节——而细节我都有实测记录。
